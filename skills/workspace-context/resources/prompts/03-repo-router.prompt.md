## Role:

You are a Multi-Repo Task Router. Given the per-repo mini-skill indexes already generated by `02-context-skill.prompt.md`, you produce ONE top-level routing artifact (`_repo_router.json`) that an agent reads BEFORE anything else to decide **which repo(s) a task touches**.

This is the agent's first decision. File-level routing inside a repo comes later.

## Objective:

Emit a single JSON block representing `<workspace>/.asta-context/_repo_router.json`. The block must contain:

1. **`request_buckets`** — a hand-built map of task-vocabulary phrases → impacted repos. Built from each repo's `scenarios` arrays + cross-repo flow analysis. This is the agent's substring lookup table.
2. **`flows`** — a map of named end-to-end flows that span multiple repos, with the ordered repo chain and the `_global_links.json` topics that wire them together.
3. **`per_repo_summary`** — one-paragraph summary per repo describing what work belongs there. Used when the agent has to decide between multiple matches.
4. **`disambiguation_rules`** — explicit "if both A and B match X, prefer A unless …" rules. Eliminates token collisions like `tms` matching both booking and AP service.

The output is the source of truth for the agent's repo-selection step. `_scenarios.json` (file-level) and `_global_index.json` (file-level) are read AFTER this.

## Context:

Inputs already on disk:

- `<workspace>/.asta-context/repos/<key>/_index.json` for every registered repo.
  Each `files[]` entry has `primary_for`, `mentions`, `scenarios`, `domains`, `capabilities`.
- `<workspace>/.asta-context/_global_links.json` — cross-repo edges with `topic_or_endpoint`, `producer`, `consumers`, `protocol`, `schema_path`. **REST convention:** `producer` = the CALLER (client), `consumers` = the CALLEE (server). Model every cross-repo REST call this way — the resolver promotes the callee into scope when a caller changes a named request contract. Capture a distinct edge per endpoint that carries a real data contract (not just health checks).
- `<workspace>/.asta-context/repos/<key>/runtime/*.md` — flow files (read titles + summaries; full body not needed).
- `<workspace>/.asta-context/workspace.yml` (draft) — repos + depends_on.

## Instructions:

### 1. Build `request_buckets`

For every `scenarios` phrase across all repos' `_index.json`:

```
bucket[phrase] = unique(repos where this phrase appears in any file)
```

Then add **cross-repo phrases** that don't appear in any single repo's scenarios but describe end-to-end flows. Examples:

- "service plan to email" → all three repos
- "booking sent but no email" → booking + AP + email
- "ap not picking up booking event" → booking + AP

Use `_global_links.json` to identify which repo chains exist, and name them naturally.

### 1b. Coverage check — enforced by validator

These rules are checked by `resources/validate-router.js` after you emit the router. **Do not emit a router that fails the validator**; if you suspect any rule may fail, fix before emitting.

1. **Every `primary_for` token in every repo's `_index.json` MUST be reachable from at least one `request_bucket` key.** Iterate over the union of all `primary_for` arrays. For each token T, confirm there exists at least one bucket phrase that includes T as a substring (with hyphens converted to spaces). Missing tokens → add a bucket entry naming that concept in user vocabulary.
2. **Every concept token MUST have at least two synonym buckets.** A concept named `temporal-workflow-execution` needs both `"workflow restarting"` and `"workflow keeps restarting"` (and ideally `"continueAsNew triggered"`, `"workflow history overflow"`). Single-bucket coverage = the agent misses real phrasings.
3. **Every collision token in `workspace.yml.routing_rules` MUST have a `disambiguation_rules` entry.** Walk routing_rules; for every rule whose `repos` array length > 1, the `disambiguation_rules` list must contain an entry with `token == rule.match[i]` for each ambiguous token.
4. **Every flow MUST have ≥ 5 triggers, all lowercase, all unique across the file.** Enforced by validator.
5. **Every flow's `repo_chain` MUST be a valid path in `_global_links.json`.** Enforced by validator.

Failed validation → the SKILL.md Step 7b instructs the orchestrator to re-run this prompt with the failure list called out. Coverage gaps are the root cause of "agent loads 6 files defensively because no bucket matched."

### 2. Build `flows` — DETERMINISTIC

`flows` is built by a precise algorithm over `_global_links.json`, **not** by free LLM construction. Re-running the prompt MUST produce the same `repo_chain` and `topics` for the same input.

#### 2a. Topology — pure algorithm

Treat `_global_links.json` as a directed multigraph:
- **Node** = repo key.
- **Edge** = one entry `{topic_or_endpoint, producer, consumers[]}` — produces an edge from `producer` to each consumer.

Run the following:

```
1. Build adjacency map: edges[producer] = [{to: consumer, topic, protocol, schema_path}, …]
2. Identify SOURCE nodes: every node with at least one outbound edge whose key does NOT appear as
   any consumer in the whole graph (or that has more outbound than inbound edges).
3. For each SOURCE node S, do a BFS up to depth 3:
   - Path 0: S
   - Path k+1: extend every path-of-length-k by every outbound edge whose `to` is not already in the path.
4. Emit one flow per UNIQUE path of length ≥ 2 (i.e., ≥ 2 hops, i.e., ≥ 3 nodes — single-edge pairs are NOT flows).
   - If a 3-node path P shares its first 2 nodes with a 2-edge path Q, KEEP both: Q is the explicit shorter journey.
5. Cap at 10 flows. If more candidates exist, prefer:
   a. paths whose topics have schema_path != null
   b. paths whose topics appear in any repo's primary_for
   c. longest paths first
```

#### 2b. Flow object shape

Each flow MUST have these fields:

```json
{
  "name": "<kebab-case derived from source-and-sink topics>",
  "description": "<one sentence; LLM may compose this freely>",
  "triggers": ["<lowercase phrase>", "<lowercase phrase>", …],
  "repo_chain": ["<repo>", …],
  "topics": [
    {"topic": "<name>", "protocol": "<kafka|rest|…>", "from": "<repo>", "to": "<repo>", "schema_path": "<path|null>"},
    …
  ],
  "entry_files": { "<repo>": "<path under repos/<repo>/>", … }
}
```

#### 2c. Name derivation (deterministic)

```
name = kebab(first_topic) + "-to-" + kebab(last_topic)
```

For a single-topic flow: `name = kebab(topic) + "-flow"`.

#### 2d. `triggers[]` — agent matching keys

This is the array the agent matches against the user's task text, NOT `name` or `description`. Build it as:

```
triggers = union(
  every `scenarios` phrase from any entry_file's front matter,
  for each topic in the flow: ["<topic-name lowercase>", "<topic-name> event", "<topic-name> not received", "<topic-name> failed"],
  user-vocabulary paraphrases of the flow's business intent (3–5 phrases, lowercase, no punctuation)
)
```

Every trigger phrase MUST be:
- lowercase, hyphens converted to spaces
- 2–6 words long
- distinct from every other flow's triggers (no overlap with other flows' triggers — if a phrase matches two flows, drop it from both and add a more specific one)

Minimum: 5 triggers per flow. Maximum: 15.

#### 2e. `entry_files` — pick per repo

For each repo in `repo_chain`, pick the entry file as follows (in order; first hit wins):

1. The `runtime/*.md` file whose front-matter `topic_or_endpoint` matches the flow's topic for that hop.
2. The `runtime/*.md` file whose `scenarios` array contains the flow's intent phrase.
3. The largest `runtime/*.md` file in that repo (most coverage).

If a repo has no `runtime/*.md`, fall back to its `navigation/scenarios.md`.

#### 2f. Determinism check

Re-running steps 2a–2e on the same `_global_links.json` MUST produce byte-identical `repo_chain` and `topics` for every flow. Trigger arrays may differ in phrasing across LLM runs but MUST include every topic-derived phrase from 2d.

### 3. Build `per_repo_summary`

For each repo, write 1–3 sentences answering: **what work belongs in this repo?** Use the repo's `domains` + the top 3 capabilities by file count. Example:

```json
{
  "example-booking-service-1": "Owns inbound ServicePlan consumption from upstream, RFP / amend / cancel / pricing variant routing, and Temporal workflow start. All booking-side REST endpoints (/bookings, /transport-orders, /customs-orders). Does NOT own customs dispatch — that lives in activityplanworkflow."
}
```

### 4. Build `disambiguation_rules`

Walk every token that appears in more than one repo's `routing_rules` (i.e., collision tokens). For each, write an explicit rule:

```json
{
  "token": "tms",
  "default_repo": "example-booking-service-1",
  "rule": "TMS dispatch from booking-side (SAP-TMS/Non-SAP routing, SEND_TO_TMS event, CAMS check) lives in booking-service-1. AP-side TMS publishing (PublishTmsActivityImpl, AmendmentSendToTmsImpl, tms-topic produce) lives in activityplanworkflow.",
  "AP_marker_phrases": ["publish to tms", "tms activity", "amendment send to tms"],
  "booking_marker_phrases": ["send to tms endpoint", "sap-tms feedback", "tms country routing"]
}
```

Cover every token whose `repos` array has length > 1 in `workspace.yml.routing_rules`.

### 4b. Build `glossary` — vocabulary grounding (CRITICAL)

Tickets speak business language; the code uses different names. Un-grounded, this causes TWO failures: the router misses (the ticket word is in no bucket) AND the implementer invents a field from the ticket word instead of the real symbol (e.g. writes `flow` when the code field is `transportActivity`). The glossary closes both.

For each domain concept whose ticket vocabulary differs from the codebase symbol, emit one entry:

```json
{
  "aliases": ["flow", "flow type", "service type", "direction", "import export"],
  "canonical": "transportActivity",
  "values": ["EXPORT", "IMPORT"],
  "type": "String enum",
  "owner_repos": ["<repo that defines it>", "<repos that use it>"],
  "source": "<repo> <Class.field> (file:line)",
  "notes": "Never introduce a new field named flow/serviceType — bind to transportActivity."
}
```

How to derive (deterministic-ish):
1. Scan each repo's `domain/*.md` + `contracts/*.md` for fields with a small **enum** value set (`EXPORT|IMPORT`, `IMPORT|EXPORT`, status enums) and for **DTO/entity field names** that carry business meaning.
2. For each, list the natural-language `aliases` a ticket would use (synonyms, abbreviations, the spaced/hyphenated forms). Aliases must be SPECIFIC — never generic words (`data`, `type`, `service`) that would over-match.
3. `canonical` = the exact symbol as written in code. `values` = the enum literals (or null). `owner_repos` = every repo whose `_index.json` shows the symbol in `primary_for`/`mentions`.
4. `source` = the defining `file:line`. `notes` = the anti-drift instruction.

Emit entries for at least: every enum field crossing a repo boundary, and every concept whose common ticket word ≠ code symbol. Skip 1:1 matches (ticket word == code word).

After writing, the orchestrator runs `node <workspace>/.asta-context/hooks/../../validate-router.js` (path resolved by SKILL.md Step 7c). Validator failures abort the write — fix and re-emit.

## Notes:

- `flows` is **deterministic** (Section 2). `request_buckets`, `per_repo_summary`, `disambiguation_rules`, and `glossary` (Section 4b) need language judgment and are LLM-generated.
- `glossary` is the single highest-leverage section for the two most common real-world failures: routing misses on business vocabulary, and the implementer inventing a new field name for an existing concept. A concept whose ticket word differs from the code symbol and has no glossary entry WILL drift.
- The agent's Boot 0 matches tasks against `flow.triggers[]` (Section 2d) — NOT `flow.name` or `flow.description`. Trigger coverage is what makes routing work in practice.
- The agent's Boot 0 order is: `workspace.yml` → `_repo_router.json` → `_symbols.json` (identifier lane — class names + abbreviations short-circuit to one file) → `_scenarios.json` (NL phrases, only if repo router didn't resolve) → `_global_index.json` → `_global_links.json`. So this file's coverage is the difference between "agent loads two files" and "agent loads twenty".
- Disambiguation rules are the single highest-leverage section for collisions. A collision token without a rule is a validator failure.
- `flows` count is bounded by the graph topology (Section 2a step 4) — typically 3–10 for a 3-repo workspace. Do not pad.
- `per_repo_summary` is read when the agent is unsure. Keep it sharp — explicit "does NOT own X" lines are valuable.
- Re-run this prompt after any per-repo `_index.json` regeneration. The validator MUST pass before the orchestrator writes the file.
